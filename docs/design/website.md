# Website cometcast.de: rebuild

Status: specification, to be built. Replaces the current site (`site/`, generated by `tools/build-site.mjs`)
completely. The agreed look is `docs/design/website-pitch.html` (open it in a browser; the "Pitch" header
and the board labels are not part of the site). Where this file and the pitch differ, this file wins.

## Audience and tone

* The home page is for people who are **not** technical: teachers, office staff, club members. It answers
  one question: "What do I need to send from my device to this screen?"
* Technical details (data path, servers, libraries) live on their own page, linked from the footer only.
* Write from the user's side: what they get, what they do. No statements about what the project built,
  tested or measured. Beta is a small badge with "Try it out" and nothing more; no lists of what is
  verified. No `UNCERTAIN` wording on the site.
* German uses informal "du" (as the apps do).

## Languages and paths

* **English is the default** under `/`; **German** mirrors it under `/de/` with German slugs.
* Pages (EN / DE):
  * Home: `/` / `/de/`
  * Download: `/download/` / `/de/download/` (what to install per device, linking app stores and releases
    when they exist; "coming soon" otherwise; no status table of internals)
  * How it works (technical): `/how-it-works/` / `/de/so-funktionierts/` (data path diagram, what the relay
    sees and stores, own server/TURN, signed announcements and connection check code in plain words, the
    open-source building blocks table with "stays in your network" / "goes to the relay")
  * Privacy: `/privacy/` / `/de/datenschutz/`
  * Host it yourself: `/self-hosting/` / `/de/selbst-hosten/`
  * Open source: `/open-source/` / `/de/open-source/` (licence, source link, third-party components)
  * Contact: `/contact/` / `/de/kontakt/`
  * Imprint: `/imprint/` / `/de/impressum/` (same placeholder rules as today: `noindex`, public build fails
    while required branding fields are empty)
  * 404 page, `sitemap.xml` with both languages, `robots.txt`, `CNAME`, `.nojekyll`.
* Every page has `<link rel="alternate" hreflang="en|de|x-default">` to its counterpart, and the header's
  language switch links to the counterpart page (not to the other home page).
* **Language hint:** a small bar at the top, shown only when the browser's preferred language
  (`navigator.languages`, first one that is `en` or `de`) is a language the site offers **and** differs from
  the page's language. "This page is also available in German. / Read in German ×" (and the German
  counterpart). Closing it stores the choice in `localStorage` (try/catch) and it does not come back;
  following its link also stores it. No automatic redirect. Without JavaScript nothing shows.
* **Links that must keep working or be redirected:** the old paths (`/funktionsweise/`, `/downloads/`,
  `/datenschutz/`, `/impressum/`, `/kontakt/`, `/open-source/`, `/en/...`) get small redirect pages
  (meta refresh + canonical + link) to the new paths. Update `branding/cometcast.json`
  (`privacy_url`, `imprint_url`) to the new URLs and fix every place that uses them (`tools/branding.test.mjs`,
  `apps/web/tests/round5Web.test.ts`, `apps/flutter/lib/src/branding_info.dart` and how it is generated,
  any other hit of `cometcast.de/datenschutz`, `/impressum`, `/en/`).
* Do not break the web app under `/app/`, the join links `cometcast.de/{CODE}` and `/app/{CODE}`, the
  `.well-known` files, and the `404.html` handling that `pages.yml` and `docs/website.md` describe (read
  them; the site's own 404 must keep doing what it does now for join codes).

## Look (from the pitch)

* Tokens, colours and type as in the pitch's `:root`: night-sky navy, comet amber as the one accent, a
  slightly blue paper ground; Bricolage Grotesque (headings), Atkinson Hyperlegible (text), JetBrains Mono
  (room codes). **Automatic dark mode** with `prefers-color-scheme` (no toggle needed); both themes designed.
* **Fonts are self-hosted from npm `@fontsource` packages** (`@fontsource-variable/bricolage-grotesque` or
  `@fontsource/bricolage-grotesque`, `@fontsource/atkinson-hyperlegible`, `@fontsource/jetbrains-mono`), only
  the weights and the latin / latin-ext subsets used, copied into `site/assets/fonts/` by the build. No CDN,
  nothing from third parties. Add the fonts (OFL) to `THIRD_PARTY_NOTICES.md` and the open-source page.
* **Header:** logo + name, "What you need" (anchor to the finder on the home page; on other pages it links
  to the home page's finder), "Download", language switch, primary button "Open web app". One line on
  desktop; on phones it wraps tidily (or a simple menu), never the old two-row mess.
* **Footer:** several columns as in the pitch's first version (Product: Web app, Download, What you need;
  Trust: Privacy, Host it yourself, Open source, How it works (technical); Project: Contact, Imprint,
  GitHub), plus the short line "Free software, no cookies, nothing loaded from third parties". It is
  **quiet**: a slightly grey background token of its own, smaller text, muted link colour, no strong
  colours. Not the dark band.
* **Home page**, top to bottom:
  1. Hero: headline, one sentence, buttons "What do I need?" (to the finder) and "Open web app", the
     Beta badge with "Try it out. Free, no account." On the right the **display screen drawn as the real web
     display looks** (room name, approval pill, step 1 "Open in your browser: cometcast.de", step 2 "Enter
     this code", QR code, "No download needed.", Settings). The address shown is the site's domain
     (`cometcast.de`, from the branding file, no port). Faint stars behind the hero.
  2. The finder "What do you need?" (see below), right below the hero.
  3. "Then it is three steps" (screen shows a code; enter or scan; present, with pause).
  4. Footer.
* **Finder:** exactly the matrix of the pitch's script (`M` in `docs/design/website-pitch.html`, current
  version), with both languages. Each answer: whether it works, then each way with "On your device" and
  "On the screen" chips (Nothing to install / Open cometcast.de / Comet Cast app / built in), easiest first,
  a short plain note where the pitch has one. Keep the device pictograms.
  * **Works without JavaScript:** the static HTML contains the full answer table (device × screen, all
    ways) as a readable table or list; the script turns it into the interactive picker and hides the table.
    The selected pair may be kept in the hash (`#laptop-appletv`) so it can be linked.
  * Keyboard accessible (buttons with `aria-pressed`, result in an `aria-live` region), visible focus.
* No other JavaScript on the site besides the language hint and the finder; both are small inline or
  one shared file, no frameworks.

## Build and checks

* Keep the generator approach (`tools/build-site.mjs` + `site-content/*.md` for legal texts + branding
  file), rewritten as needed. All page text in one place per language (e.g. a strings module), so EN and DE
  stay in step; a check fails the build when a key is missing in one language.
* `tools/check-site-links.mjs` checks every internal link, hreflang pairs, that every page exists in both
  languages, and the redirects. Update `pages.yml` (npm ci for the font packages) and `docs/website.md`.
* Screenshots: write `tools/site-screenshots.mjs` (Playwright, already installed; `chromium.launch()`
  needs no options) that shows home, how-it-works and download in EN and DE, light and dark, 1440 and
  390 px wide, into a directory given as argument. Note: `page.screenshot({fullPage:true})` fails in this
  environment; set the viewport height to the page's `scrollHeight` instead.

## Amendments (round 3)

Decided by the product owner after the pitch; they replace the matching parts above.

1. **Hero buttons.** The primary hero button is **Download** (to the download page), the secondary one "Open web app". "What do I need?" is no
   longer a hero button (the finder is right below). The header keeps "What you need" as a link and "Open web app" as its primary (amber) button.
2. **Finder, new structure** (three questions, in this order):
   * **I have:** Windows laptop, Mac, Linux laptop, iPhone or iPad, Android phone or tablet.
   * **How are you connected?** (between the two device questions), three choices, default **Office or school**:
     * *Same Wi-Fi, e.g. at home*: built-in ways (AirPlay, Miracast, Cast, browser Cast) are shown normally.
     * *Office or school* (own device, guest Wi-Fi): built-in ways stay but carry the chip "Often blocked in school and office networks";
       Comet Cast ways carry "Also works across networks" and are listed first, then the built-in ones.
     * *Different networks, e.g. mobile data*: built-in ways are left out; Comet Cast ways stay with "Also works across networks".
     There is no "Not sure" choice. If nothing remains, the answer says so plainly (and that the same Wi-Fi would help).
   * **The screen is connected to:** Apple TV, Google TV / Android TV, Chromecast, Windows PC, Mac, Linux PC, Interactive board (Android).
     Mac and Linux PC are separate screens: a Mac (macOS 12 or newer) receives AirPlay on its own, a Linux PC only with the Comet Cast app. Google TV and Android TV stay one choice (the same system); the interactive board stays separate (plain Android, usually no built-in Cast receiver).
     There is no TV / projector distinction.
   * Facts of the matrix (`tools/site/finder.mjs`, easiest first, plain notes as in the pitch): Windows and Linux laptops reach Chromecast and Google TV with the
     browser's built-in Cast (Chrome or Edge; Chrome or Chromium on Linux) or with Comet Cast, Apple TV with browser + app on the Apple TV or the laptop app without an app on the TV
     (photos and videos right away, the screen with a short delay), a Windows PC with the browser on both sides (Windows laptops also with Win + K and the Comet Cast app on the PC),
     a Mac or Linux computer and an interactive board with the browser on both sides (the board also with the app on it). A Mac adds built-in AirPlay to Apple TV (first, nothing to install)
     and to a Mac or Linux computer running the Comet Cast app. An iPhone or iPad uses AirPlay or the app with Apple TV, app or browser (photos, PDFs and links only) with Google TV, a Windows PC and
     an interactive board, AirPlay + app or app + browser with a Mac or Linux computer, and cannot send to a Chromecast with Comet Cast. An Android device uses the Cast button for Google TV and Chromecast
     (Google TV also app + app), app + app or browser + app (photos, PDFs and links only) for Apple TV, Smart View or Cast (Miracast) + the app on a Windows PC or app + browser, app + browser for a Mac or Linux computer,
     and app + browser or app on the board. **A browser on a phone cannot share the screen:** its ways always say "Photos, PDFs and links only".
   * The no-JavaScript fallback is still the full table, now with a note on the network each way needs.
3. **Download page** (`/download/`, `/de/download/`):
   * Generated at build time from the latest GitHub release of the source repository (`api.github.com/repos/.../releases/latest`); asset links are the release asset URLs, mapped to Windows, macOS,
     Linux and Android by file-name pattern (names from `.github/workflows/release.yml`). `--offline`, no release or a failed call means "Coming soon" on every card. The visitor's browser loads nothing from GitHub until a download is clicked.
     App Store and Google Play links are placeholders ("coming soon") until the listings exist.
   * A tiny script (`userAgentData` / `userAgent`) moves the matching card to the top as "For your Mac" and so on; without JavaScript all cards are listed.
   * Short links: `/d/` (English download page) and `/de/d/` (German); `/apk/` leads to the latest Android APK (build-time meta refresh and link), else to the Android card of the download page. They do not collide with join codes or `/app/`.
   * The Pages workflow also runs when a release is published, so the page follows the latest release (`docs/website.md`).
