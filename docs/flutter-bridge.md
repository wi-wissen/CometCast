# Flutter bridge (Rust core in the Flutter app)

The Flutter app (`apps/flutter`) talks to the Rust core through **flutter_rust_bridge** ("FRB"). This page explains how the pieces fit and what to run after changing something. Status: milestone M1, desktop app, Linux verified (see [Verified](#verified) and [Not done](#not-done)). The content channel (images, PDFs, links) is wired in as well, see [Content](#content-images-pdfs-links).

## The picture

```
Flutter UI (Dart)          lib/*.dart
   |  CoreApi (interface)  lib/core/core_api.dart   <- fake in widget tests
   |  RustCoreApi          calls the generated code
   v
lib/src/rust/*.dart        generated by FRB  (committed)
   |  loads libcc_ffi.so   lib/core/rust_loader.dart
   v
crates/cc-ffi/src/frb_generated.rs   generated by FRB (committed)
crates/cc-ffi/src/api.rs             hand-written API (the only Rust file you edit)
   v
cc-receiver (ReceiverCore) / cc-sender (SenderCore) / cc-proto (RoomCode)
```

## Content (images, PDFs, links)

The native content channel of the Rust crates (`cc-files`, `cc-sender`'s `ContentSender`, `cc-receiver`'s `take_content_events`, `cc-docs`; format and limits in [web-m2.md](web-m2.md) and [transport.md](transport.md)) is used by the Flutter app: "Send file or link" on the send side, the receive view on the other. What the app does is in [documents.md](documents.md), "In the Flutter app". The files: `crates/cc-ffi/src/content.rs` (receiving side, mailbox, worker lookup, link check), `content_sender.rs` (sending side), the types in `api.rs`, and in Dart `receiver_controller.dart`, `presenter_session_controller.dart` and the pages under `lib/src/`.

**Receiving.** `start_receiver(..., content: true)` sets `ReceiverOptions::content`. The receiver task reads the content events in the same `select!` as the core events (content first, as docs/transport.md asks), and on `PeerLeft` it reports `PeerLeft` to the UI **first**, then hands over what is still queued (a 2 s patience per event); `stop_receiver` is polled during that drain, so a stop is not delayed by it. The events for Dart are small: `ContentTransferStarted { document, name, size }`, `ContentFrameReady`, `ContentDocumentOpened { name, pages }`, `ContentLink { url, host }`, `ContentStopped`, `ContentError { error }`. The pictures do **not** travel in the stream:

```
cc-receiver content events (Blob = Arc<Vec<u8>>, queue bounded by count 16 and 32 MiB)
   -> content.rs mailbox: ONE slot, newest wins, replaced pictures are counted
   -> ContentFrameReady (only while the previous one was not answered)
   -> Dart: take_content_frame() -> image bytes or page RGBA
```

Bounds and copies (UNCERTAIN: from reading the code, not measured): the mailbox holds one shared `Blob`; `take_content_frame` copies it once into a `Vec<u8>` and the bridge copies it once into the Dart heap, so a page of up to 127 MiB (the `cc-docs` output limit) exists up to three times for a moment, an image (at most 10 MiB) the same. A link, a stop, a new document and a refused PDF empty the mailbox, so a stale page cannot be fetched. Every receiver start and stop bumps a generation, so a task of an older receiver can neither publish nor clear. Text of the sender (the `detail` of an error, which can contain sender-chosen words) never reaches Dart; errors are the enum `UiContentError`, which the UI translates. File names were cleaned by `cc-files`; links are validated by `cc-files` and carry their host in the punycode form (`url` crate), which is what the card shows. The core never opens a link.

The width that pages are rendered at is `set_content_target_width`; the app reports the width of the view in physical pixels (and again after a resize). The last value is also used when a receiver starts.

**PDF worker.** PDFs are rendered by `cc-docs` in a resource-limited child process (docs/documents.md). `content::worker()` decides where it is, and never selects the in-process engine itself: (1) the explicit path of `set_docs_worker`, (2) the environment variable `COMETCAST_DOCS_WORKER` (left to `cc-docs`, which refuses an untrusted file), (3) a file `cc-docs-worker` **next to the running executable**, passed explicitly as `Isolation::Process(WorkerSpec)`, (4) `cc-docs`' own discovery, checked with `discover_checked()` (an untrusted `COMETCAST_DOCS_WORKER` counts as not found). When none is found, `worker()` hands out an isolation that names a program that does not exist (`Isolation::Process`), **on every platform**: `cc-docs` maps `Isolation::Auto` and `InProcess` to the in-process engine on iOS, tvOS and wasm, so passing `Auto` through would render a peer's PDF unsandboxed there; with this guard the PDF is refused before `cc-docs` can render it, and the UI shows `UiContentError::WorkerUnavailable` (decided by "no worker was found at start", not by matching text). This holds for the calls made by `cc-ffi` (receiver and the sender's page count); other users of `cc-docs` keep its own rules (`Auto` is in-process on iOS, tvOS and wasm, docs/documents.md). UNCERTAIN: tested by a unit test of the isolation chosen, not on an iOS build. The sender uses the same worker only to count pages for the presenter view; without one it sends anyway and the page count is unknown.

**Not isolated: received images.** Images (PNG, JPEG, GIF, WebP, at most 10 MiB, 64 million pixels by the header) are decoded **in-process by the Flutter engine**, not in the PDF worker; a flaw in an image codec of the engine is not contained by the sandbox. The number of frames of an animated image (GIF, WebP) is not bounded by the app (UNCERTAIN, known limit: the engine decides how many frames it decodes and how much memory they take; not measured).

**Sending.** `start_content_sender` reads the file in Rust (a regular file, at most 10 MiB for an image and 64 MiB for a PDF, `limit + 1` bytes read so a growing file or device cannot run on), checks the type by extension **and** by the first bytes for images (PNG, JPEG, GIF, WebP; the declared type is the one of the bytes), requires the `%PDF-` header, asks the worker for the page count and validates a link, all before it connects (`Prepared` or `Rejected { reason }`). The name in `Prepared` is the local file name; the Dart controller strips control and bidi-override characters and cuts it to 80 characters (`displayName`) before it is shown. Then: `Joined`, `Connected` (data channel open, waits at most 30 s), `Progress { sent, total }` (bytes handed to the channel, at most one report per percent; the channel buffers up to about 1 MiB, so the receiver can be that far behind), `Sent` (after the transport confirmed delivery). After `Sent` the sender stays connected and forwards `send_content_cmd` commands: native and web receivers drop shown content when the sender leaves. `Stop` is flushed, then the sender ends with `Stopped`. A PDF held for sending exists once (at most 64 MiB), briefly twice while the worker counts pages.

**Office files.** A path that ends in `.docx`, `.pptx` or `.xlsx` is converted to a PDF by `cc-office` before anything is connected (`crates/cc-ffi/src/office.rs`; format, limits, error mapping and the refusal reasons `OfficeUnavailable`, `OfficeEncrypted`, `OfficeFailed` are in [documents.md](documents.md#office-files-in-the-flutter-app)). The event order for such a file is `Converting { name }`, `Prepared` (kind PDF, the converted name and size), then as for a PDF. The conversion runs on `spawn_blocking` as a child process (`cc-office-worker`, found like the PDF worker next to the executable); the pure-Rust engine only. The Dart controller has a phase `converting` and the screen an indeterminate bar. Tests: Rust unit tests (error mapping, the container checks, a fake worker program that writes a PDF, a failing and a missing worker), Dart widget tests with the fake core, and `test/rust_core_test.dart` against the real library and the real `cc-office-worker` (a real `.docx` converted to `Class notes.pdf`).

Two things to know:

- **Dart's `Process.start` and the worker.** While the Dart VM tracks a child it started itself, its exit handler can reap other children of the process, including the render worker that the Rust core starts; `cc-docs` then reports `Internal("cannot watch the worker")` (seen in the integration test: after `Process.start` the page count of a PDF was unknown and every page failed; before it and after a *detached* start it worked). The app never starts a process from Dart (`url_launcher` on Linux goes through GTK/GIO), so this does not affect it; the integration test starts `cometcast-cli` detached for that reason. UNCERTAIN: found by experiment, the mechanism inside the Dart VM was not read in its source; `cc-docs` could tolerate `ECHILD` (not changed here).
- **One sender or receiver at a time.** The content sender shares the sender slot with the screen sender: starting one stops the other.

## Toolbar over the received screen

The receive view has the toolbar of the web receiver (`apps/web`, `docs/web-m2.md`): pen, highlighter, eraser, laser pointer, undo, clear all, freeze; five colours (the web colours), three sizes (pen 2, 4, 8 and highlighter 12, 20, 32 logical pixels, highlighter opacity 0.35, eraser radius 16). Code: `apps/flutter/lib/annotations.dart` (model `AnnotationController`, `AnnotationLayer`, `AnnotationToolbar`), placed by `receive_page.dart` over the live picture, a received image and a received PDF page (not over a link card). Points are stored normalised to the picture (0 to 1), so a resize or full screen keeps them in place; undo keeps up to 100 steps (the same model as `apps/web/src/core/annotations.ts`). Freeze holds a clone of the current video image while the stream keeps being decoded (the web receiver does the same); it is not offered for a still image or page. The laser dot follows a hovering mouse, or a finger or pen only while pressed. Marks, undo history and the frozen picture are dropped when the live picture ends or when the image or page underneath changes (a page turn included, like the web app). The strings are in the ARB files (en and formal de).

**There is no annotation wire format.** The task that added this asked to reuse "the existing control-channel annotation messages". There are none: the control channel carries `cmd` (`next_page`, `prev_page`, `go_to_page`, `stop`), `image`, `link` and `document` messages and their binary chunks (docs/web-m2.md), and `cc-proto`, `cc-files`, `cc-receiver` and `cc-sender` have no stroke, laser or freeze message. The web toolbar is receiver-only and its annotations never leave the tab ("Annotations are local"). So the Flutter toolbar is the same: **local to the receiving device, nothing is sent**. A sender-side toolbar (the presenter draws and the receiver sees it) would need a **new** message set with limits and tests in `cc-files`/`cc-proto`; inventing one was ruled out, so it is **not done**, and the Rust crates were not extended for annotations. The sender view also has no picture to draw on (the screen sender shows no preview, the content sender shows no page).

UNCERTAIN: the toolbar is fixed at the bottom left (the web one can be dragged and collapses to a dot; this one collapses to a button and scrolls sideways when the window is narrow); it can cover the bottom of the picture and, on a narrow window, the page indicator; there are no keyboard shortcuts for the tools (the buttons are focusable); a stylus pressure or a palm is not handled; the freeze clone costs one more copy of the picture in memory; widget tests drive pointers, nothing was tried with a real touch screen or pen.

## The picture path (receiver)

```
WebRTC task --video_tap (RTP payloads, bounded channel of 4096 packets)--> decoder thread "cc-video-decode"
   H264Assembler -> OpenH264 (cc-media, feature `h264` of cc-ffi, default on) -> RGB -> scale -> RGBA
   -> mailbox with ONE slot (newest wins)  --FrameReady event-->  Dart --take_frame()--> ui.Image -> RawImage
```

Implemented in `crates/cc-ffi/src/video.rs`; no change to `cc-receiver` was needed (the session already had the packet tap and `request_keyframe`). Why it is a pull model: a `StreamSink` queues without limit, and a pushed 8 MB picture per frame would grow memory when Dart is slow. Instead only a tiny `FrameReady` event is pushed, and only while the previous one was not answered by `take_frame`. Bounds:

- packets that the bounded tap drops (decoder too slow) are counted in `dropped_packets`, like those the decoder thread throws away;
- a decoder thread of a stopped session can no longer publish pictures or touch counters of a newer session (generation checked under the mailbox lock);
- one picture waits in the mailbox; a newer one replaces it and is counted in `dropped` (the UI was too slow);
- the decoder thread drops everything, waits for the next IDR frame and asks for a key frame if more than 2000 packets pile up (`dropped_packets`; placeholder value, not tuned); the same happens after a lost RTP packet or a decode error (`decode_errors`); key frame requests are rate limited to one per second and sent as PLI by the receiver task;
- pictures are scaled (nearest neighbour) to the size the UI reports with `set_video_max_size`, at most 1920x1080; only H.264 is decoded (other codecs, such as the VP8 test video, are only counted).

**Pass-through mode (Android hardware decoding).** With `set_video_passthrough(true)` the same decoder thread does everything up to the access unit (RTP depacketising, wait for IDR after loss, backlog limit) and then, instead of OpenH264, puts the unit into a second bounded queue (`MAX_ENCODED_QUEUE` = 8, placeholder) and sends `EncodedReady` (again only after `take_encoded_video`). If the host is too slow the queue is dropped (counted in `dropped`), the thread waits for the next IDR and a key frame is requested. The OpenH264 decoder is created only when it is first needed, so a pass-through receiver does not need the OpenH264 library at all (relevant for the `h264-libloading` release variant on Android). Switching the mode while a receiver runs is allowed (a key frame is requested). Tests in `video.rs` (queue order, bound, notification, stale generation); the end-to-end path through `MediaCodec` was never run.

Without the feature `h264` the receiver builds without a decoder and the video stats carry an error text. UNCERTAIN: the H.264 patent/licence questions of OpenH264 are open (docs/capture.md, "H.264 licensing"); the default feature builds OpenH264 from source.

Rules worth knowing:

- **Errors are events.** A start failure (server unreachable, bad or unknown room code) arrives as an `error` event, then the stream ends. Reason (observed with FRB 2.13.0 in `test/rust_core_test.dart`): for a function that returns a stream, a returned `Err` did not reach the stream listener and surfaced as an unhandled async error instead, so the API has no `Result`.
- **One receiver and one sender at a time.** Starting a new one stops the old one. `stop_*` also works while a start is still connecting: each start gets a generation number, and a start whose number is out of date after connecting closes its new core at once. Cancelling the Dart subscription alone does not stop the core immediately: the core notices at its next event (when `StreamSink::add` fails, at most about one second later while connected) and shuts down; the controllers therefore also call `stopReceiver()` / `stopSender()` explicitly. A panic inside a background task is caught and reported as an `error` event.
- **Counters are `u64`**, which Dart sees as `BigInt`; the controllers convert with `toInt()`.
- **Room-code validation is not duplicated** in Dart: the UI calls `checkRoomCode`. The Rust function reports a bad character before a wrong length so the UI can warn while someone is typing. The helper text under the code field gets length and alphabet from Rust through an ARB placeholder. The Dart test fake (`test/fake_core.dart`) has a small copy of the rule only for tests without the native library; `test/rust_core_test.dart` checks that it agrees with Rust.
- **Screen sharing** with `present_screen(Some(..))` needs the X11 capture path of `cc-sender`/`cc-capture`; `present_screen(None)` opens the system picker (Wayland portal with the build feature `wayland`, `GraphicsCapturePicker` on Windows, `SCContentSharingPicker` on macOS 14+; X11 whole desktop where a Linux session has no portal), see docs/capture.md, "Desktop capture with the system picker". `capture_info` was not changed: it still describes the X11 path only. `capture_info` runs the X11 connection on a blocking thread and decides "Wayland" from the environment (`XDG_SESSION_TYPE`, `WAYLAND_DISPLAY`) unless a display is forced. The Flutter app reads the forced display from `COMETCAST_CAPTURE_DISPLAY` (development and tests).
- `udp_bind` (optional) is a development switch: bind WebRTC to one local address, for example `127.0.0.1:0` for tests on one machine. The app reads it from the environment variable `COMETCAST_UDP_BIND`. UNCERTAIN: whether the default (`0.0.0.0:0`) connects two peers on one machine was not tested; the smoke tests use `127.0.0.1:0`.

## Generated code: committed, deliberately

`crates/cc-ffi/src/frb_generated.rs`, `apps/flutter/lib/src/rust/*.dart` (including `api.freezed.dart`) are **committed**. Reasons: builds do not need the code generator (or `build_runner`, which creates the `.freezed.dart` file), the build is reproducible, and reviewers see what an API change does. Cost: generated diffs in pull requests. The CI workflow regenerates the code and fails if the committed files differ. The Dart files are excluded from `flutter analyze` (`analysis_options.yaml`) and carry the generator's own header instead of an SPDX line; the license of the repository applies.

Regenerate after editing `api.rs` (inside `apps/flutter`; keep type names in `video.rs` different from those in `api.rs`: the codegen warned when both had a struct called `Slot`):

```sh
cargo install flutter_rust_bridge_codegen --version 2.13.0 --locked   # once
flutter_rust_bridge_codegen generate
```

The version of the codegen, of the `flutter_rust_bridge` crate (`crates/cc-ffi/Cargo.toml`, pinned with `=`) and of the Dart package (`apps/flutter/pubspec.yaml`) must be the same; the generator checks this. 2.13.0 is the newest stable release found on crates.io and pub.dev on 2026-11-06 (2.14.0 was still beta). The Dart SDK constraint (`>=3.13.0`) is what `flutter pub get` needs for the current dev dependencies (freezed 4.x). The config is `apps/flutter/flutter_rust_bridge.yaml`. The generator needs `freezed` and `build_runner` in `dev_dependencies` (and `freezed_annotation`) because the event enums carry data.

## `unsafe` and the lint table

The workspace forbids `unsafe_code`. FRB's generated code needs `unsafe` (it calls into C). So `cc-ffi` has its **own lint table** in `crates/cc-ffi/Cargo.toml`: `unsafe_code = "deny"` (not `forbid`, which cannot be overridden), and only the generated module has `#[allow(unsafe_code, missing_docs, clippy::all)]` in `lib.rs`. Hand-written code in `api.rs` must stay free of `unsafe`; the compiler enforces it. The other lints are copied from the workspace table by hand (Cargo cannot extend a table); keep them in sync. `unexpected_cfgs` lists `frb_expand`, a cfg name used by the FRB macros.

## Build integration (Linux)

Chosen mechanism: a small **CMake step** in `apps/flutter/linux/CMakeLists.txt`, not cargokit. Reason: it is short and readable, and the Rust crate lives in the repository's Cargo workspace (cargokit expects the crate inside a Flutter plugin folder). Cargokit is the usual choice once Android, iOS and macOS are added; revisit then.

What the CMake step does during `flutter build linux` / `flutter run -d linux`:

1. Runs `cargo build -p cc-ffi [--release]` on the workspace `Cargo.toml`. Debug builds use the cargo dev profile, profile/release builds use `--release` (the workspace release profile uses LTO and is slow).
2. Uses its own target folder `build/linux/x64/<mode>/cargo-target`, so the result does not depend on `CARGO_TARGET_DIR`. The first build compiles all dependencies (a few minutes with a cold cache).
3. Installs `libcc_ffi.so` into `bundle/lib/` next to `libflutter_linux_gtk.so`.

At start-up `lib/core/rust_loader.dart` looks for the library in this order: the file named by `COMETCAST_FFI_LIB`; `lib/` next to the executable; the plain name `libcc_ffi.so`. Tests find `target/debug/libcc_ffi.so` of the workspace (`cargo build -p cc-ffi`) and skip the real-library tests if it is missing.

The same step builds the **PDF worker**: it runs `cargo build -p cc-ffi -p cc-docs` (the `cc-docs-worker` binary comes with `cc-docs`' default feature `worker-bin`) and installs `cc-docs-worker` **next to the executable** (`bundle/cc-docs-worker`, `install(PROGRAMS ...)`), not into `lib/`: `cc-ffi` looks for it in the directory of the running executable and passes that path to `cc-docs` explicitly (see [Content](#content-images-pdfs-links)). `integration_test/content_e2e_test.dart` checks that the file is there and that `docs_worker_path()` names it without `COMETCAST_DOCS_WORKER`. The worker is a normal program of the same user: it restricts itself with Landlock and seccomp where the kernel allows it, and `docs/documents.md` says what that does and does not protect.

Android: both workers are built by cargo-ndk in `app/build.gradle.kts`, packaged as `libcc_docs_worker.so` / `libcc_office_worker.so` and found through `nativeLibraryDir`; see [android.md](android.md), "PDF and Office on Android" (built, never run on a device). The remaining platforms (UNCERTAIN, none of this was tried; everything said here for `cc-docs-worker` holds for `cc-office-worker` too, except that iOS and tvOS cannot start the child process at all and so cannot convert Office files): macOS needs the same file as a code-signed helper in the bundle. Windows: `apps/flutter/windows/CMakeLists.txt` builds `cc_ffi.dll`, `cc-docs-worker.exe`, `cc-office-worker.exe` (and `cc_miracast_ffi.dll`, [miracast.md](miracast.md)) with cargo and installs them next to the exe (never run on Windows); iOS and tvOS cannot start a child process at all, so PDFs there would need the weaker in-process engine (not selected by `cc-ffi`) or rendering on the sender. Until then PDFs on those platforms fail with `WorkerUnavailable` (translated note, nothing crashes).

The same step also builds the **Office conversion worker** (its own `cargo build -p cc-office`: `cc-office-worker` with the pure-Rust engine, which brings the large Typst-based dependency tree; the first build takes several more minutes and a few hundred MB of disk. It is a separate command because `cc-ffi` links `cc-office` with `default-features = false`, so that Typst is not in `libcc_ffi.so`; a common `-p cc-ffi -p cc-office` would unify the features and link it again) and installs it **next to the executable** (`bundle/cc-office-worker`), where `cc-ffi` looks for it (`office.rs`). Without it Office files are refused with `OfficeUnavailable` (translated sentence). `integration_test/content_e2e_test.dart` checks that the file is there and that `office_worker_path()` names it, and has a test (B2) in which the app converts a generated `.docx` and sends the PDF to `cometcast-cli receive`.

The Linux runner also sets the window title and the window icon (`assets/icon.png`, found in the bundle's `data/flutter_assets`).
