How it works

Devices find each other with a room code. Then Comet Cast tries the connection routes in order.

1. Room code

The receiver creates a room code, also shown as a QR code. The sender enters it. The code is short; the server slows guessing with limits and temporary bans.

2. Connection routes, in this order

  1. Direct. WebRTC between the two devices.
  2. Through a server. If direct fails: an organisation's server with a TURN relay (and optionally an SFU).
  3. Own Wi-Fi. If that fails too: the receiver's own Wi-Fi.

The order is the plan. Little is measured so far: connections on a local network and a TURN test on a single machine. Across real networks, through NAT, or between two devices over TURN it is UNCERTAIN.

How the app finds the server

  1. MDM policy
  2. DNS-SRV record _cometcast._tcp
  3. Announcement from the display device
  4. Built-in default list

mDNS runs in parallel for local discovery. Parts of the server discovery in the apps are not built yet.

What the server does

The server only mediates: rooms and signalling. The open server stores and relays no images, files or media. The screen travels directly between the devices or, if needed, through TURN. More on Privacy & self-hosting.
